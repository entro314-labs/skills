# Failure modes and checklists

## Timetable export

| Failure | Cause | Fix |
| --- | --- | --- |
| Non-empty cell missing from calendar | Assumed a repeated course name makes a later cell redundant | Compare final groups against every non-empty source cell; keep a per-cell checklist (coverage file) |
| Week range looks cleaner than source | Guessed a range from punctuation | Keep the literal meaning; mark `needs_confirmation` |
| Second half of a cross-slot class lost | Read one cell only | Check the adjacent slot; merge only after metadata equality |
| All dates shifted one week | Used semester start instead of the Monday of week 1 | Ask for the week-1 Monday; restate the baseline before export; check it is a Monday |
| Right dates, wrong clock times | Reused another term's period table | Require the current period table; record the slot mapping in the manifest |
| One-off session repeats weekly | Converted an explicit date to weekly recurrence | Keep explicit dates as `dated` groups |
| Weekend/lab session disappears | Latest message treated as authoritative | Per-course source refs; surface conflicts |
| Export works only on author's machine | Third-party parser on the main path | Stdlib for `.ics`; parsers optional |
| Courses fail to merge | Location spelled differently per cell | Normalize `location` to one stable string |
| Times off by an hour for part of term | Fixed UTC offset instead of IANA zone | Use IANA zone and convert each occurrence on its own date |

## Message extraction

| Failure | Cause | Fix |
| --- | --- | --- |
| Stale forward becomes an event | Date filter on receive time; header date is the original | No date filter; processed index; check event date is in the future |
| Duplicate events after re-run | No processed index or no recorded event IDs | Index by message ID; wrapper records IDs |
| Reply notifications turned into events | Accept/decline mails not filtered | Skip automated calendar responses first |
| Silent 09:00-17:00 default | Default time applied unannounced | Ask, create all-day, or flag "time assumed" |
| Wrong date accepted | Day-of-week not shown or not checked | Show weekday; compare with weekday in text |
| 03/04 read as the wrong month | Locale guess | Ask when both parts are 12 or less |
| Deadline buried in description only | One item created for event+deadline | Create the separate `DEADLINE:` reminder |
| Event created without consent | Treated forwarding as approval | Always confirm; forwarding is not confirmation |
| Cancellation ignored or duplicated | Searched by title only | Use tracked event ID, then date-window query |

## Pre-write checklist (messages)

- [ ] ID not already processed; not a calendar reply.
- [ ] Date, weekday, time, zone note, title shown to the user.
- [ ] Duplicate lookup done in all three layers.
- [ ] Deadline reminder planned where a deadline exists and is still in the future.
- [ ] Confirmation received for exactly these items.
- [ ] Write wrapper will record event IDs.

## Pre-export checklist (timetables)

- [ ] Timezone, period table, week-1 Monday supplied by the user for this run.
- [ ] Sources ranked; conflicts surfaced and resolved.
- [ ] Manifest verification pass clean; coverage check clean both ways.
- [ ] No `needs_confirmation` items left in the export.
- [ ] `.ics` generated by the stdlib path, re-parsed, four spot checks reported.

## Run order

Timetable: confirm week-1 Monday, slot times, timezone -> normalize every non-empty cell -> compare to primary source -> add supplementals and mark conflicts -> minimum questions (rounds) -> coverage check -> generate `.ics` -> validate and spot-check four classes (weekly lecture, odd/even, merged cross-slot, supplemental/weekend) -> report.

Messages: load processed index and config -> select messages (mode, unread, not processed) -> drop RSVP notifications and ignored items -> extract candidates with weekday and URLs -> dedupe, mark updates -> present numbered candidates and wait -> create/update confirmed items, store IDs, create deadline entries -> mark processed, read/archive, log, store the rest as pending.

## Final report

```
Output: <path or created entries>
Events: <n> (<n> confirmed by user, <n> excluded as needs_confirmation)
Ambiguities and answers: <list>
Remaining manual interpretations: <list or none>
Checked against: <one source | several: ids>
Spot-checked: <four classes or entries>
```

## Caveats about this guidance

- The 24-hour undo window and the 3-reminder auto-dismiss are conventions for when you maintain state; they are defaults, not protocol requirements.
- Example dates, room names and the sample period table are illustrative only; never reuse them for a real user.
