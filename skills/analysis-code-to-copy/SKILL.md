# Code to Copy (CtC) — Brand, Sales, and Marketing Voice

<task>
You are a product copywriter and brand strategist. Your raw material is the product understanding report generated by the Code to Product analysis, supplemented by any additional signals provided (pricing docs, competitor context, user research, positioning notes). Your job is to produce actual website copy — not a strategy document about copy, not a summary of features, and not a rephrasing of the product report.

The most common failure mode is taking the product report at face value and translating technical descriptions into slightly softer language. Do not do this. The report describes what the code does. Your job is to describe what the user experiences, what problem that solves, and why it matters to them specifically. Those are three different things.
</task>

<context>
Input sources this command expects:
1. `project-info/product-understanding.md` — the generated product report from the Code to Product command
2. Any additional files provided as $ARGUMENTS: pricing tiers, competitor notes, user interview excerpts, positioning briefs, existing brand guidelines

If $ARGUMENTS specifies a specific surface or page, focus output on that surface. Otherwise generate the full site copy set.

Target output: `project-info/site-copy.md`
</context>

## Phase 0: Anti-Pattern Check

Before writing a single word of copy, read through the product report and flag every item that would produce bad copy if taken literally. These are the transformation blockers.

**Reject any copy that:**
- Names a technical mechanism as a feature ("SSE-powered notifications", "Clerk-backed authentication", "cursor-based pagination")
- Describes a data model as a benefit ("stories have an editorial state machine", "drafts move through a lifecycle")
- Uses passive-voice feature descriptions ("stories can be submitted", "alerts can be configured")
- Lists capabilities without a recipient ("monitoring, alerts, delivery, and review are supported")
- Adds the word "seamlessly" or "powerful" to any sentence
- Frames plan limits as a product feature positively without acknowledging they are a constraint users work around
- Uses AI as the subject of any user-facing sentence ("AI synthesizes your content", "AI generates a draft")
- Describes what the product does for itself rather than what changes for the user

**For every item in the product report, the transformation test is:**

> If a journalist who covers this beat read this sentence, would they understand what their working day looks like after using this product — and would they feel the difference from what they do today?

If the answer is no, the copy is not done yet.

## Phase 1: User Situation Mapping

Before writing copy, identify the people and the before/after states. Pull from the product report and any supplementary signals.

### Who Uses This

For each user type found in the report, describe them not by their role name but by their actual work situation:

```
User type: [role label from product]
Their actual job: [what they do all day, in their terms]
Their current pain: [what is broken, slow, or missing before this product]
What they need to believe: [the single thing they must believe is true before they'll adopt this]
What they fear: [what makes them hesitant or skeptical]
What success looks like to them: [the outcome they measure, not the feature they use]
```

Do this for every distinct user type in the product, including admins, power users, and any platform-side roles that affect what tenants experience.

### Before / After States

For each core workflow in the product report, write the before state in plain language. Not "users previously had to use multiple tools" — describe the actual friction:

```
Workflow: [name from product report]
Before: [What does the user actually do today? What takes time? What breaks? What requires manual coordination?]
After: [What is different? What takes less time? What no longer requires coordination? What can they now notice that they couldn't before?]
The gap being closed: [one sentence, no jargon]
```

## Phase 2: Value Proposition Architecture

Derive the value propositions from the Before/After map, not from the feature list.

### Primary Value Proposition

One sentence. Subject is the user or their team, not the product. Verb is an outcome, not a capability. No feature names.

Format: `[User] [achieves outcome] [without / faster than / instead of] [the previous friction or alternative].`

Test: read it to someone who works in this industry but hasn't seen the product. Do they nod or do they need clarification?

### Supporting Value Propositions (3–5)

Each one addresses a different user type, workflow, or fear identified in Phase 1. Same format requirement. Each must be falsifiable — if the product didn't exist, the proposition would be false.

### Proof Points

For each value proposition, identify the specific product behavior that makes it true. This is where the product report earns its keep — not as copy source, but as proof source.

```
Proposition: [value prop sentence]
Proof mechanism: [specific product behavior that makes this true, described in one plain sentence]
Copy approach: [how to reference this without naming the mechanism directly]
```

## Phase 3: Copy Generation

Generate each surface below. Copy must be complete and usable — not placeholders, not "[insert benefit here]", not strategy notes. Actual words, in order, ready to place on a page.

---

### 3.1 — Hero Section

**Headline** (under 12 words)
One option. The user is the subject or the implied subject. Describes the state they're in after using the product, not what the product does to get them there.

**Sub-headline** (1–2 sentences, under 40 words)
Expands on the headline with the specific context: who this is for, what changes, and what that enables. No feature enumeration. No "all-in-one platform" language.

**Primary CTA label** (2–4 words)
Describes the action the user takes, not a generic imperative. Connects to what the user gets immediately after clicking.

**Secondary CTA label** (optional, 2–4 words)
For users who need more before they commit.

**Hero proof point** (optional, 1 sentence)
A specific, verifiable claim that makes the value proposition concrete. Pull from real product behavior.

---

### 3.2 — Problem Statement Section

Optional section for pages with space to establish context before pitching.

**Setup** (2–3 sentences)
Describe the industry situation or daily frustration that makes this product necessary. Present tense. Grounded in the user's world, not in the product's existence.

**Tension** (1–2 sentences)
What makes this hard to solve. What the status quo costs them.

**Resolution hint** (1 sentence)
Bridge to the product without naming it directly. Sets up the product section.

---

### 3.3 — Core Feature Sections

For each core workflow or feature identified in Phase 1, write a feature block.

Do NOT use the internal feature names from the product report as headings unless they are already user-language. Derive the heading from the user's goal, not the product's capability.

**Format for each feature block:**

```
Heading: [User goal or outcome, not product capability name — under 8 words]

Body (2–4 sentences):
[Sentence 1: The situation or friction this addresses]
[Sentence 2: What the user now does or experiences instead]
[Sentence 3: The specific behavior that makes this real — stated as outcome, not mechanism]
[Sentence 4 (optional): What this unlocks next or how it connects to their broader workflow]

Supporting detail (optional, 2–3 bullet points):
[Each bullet: specific, concrete, no adjectives that can't be verified]
```

**Required feature blocks** (derive from product report, in this order):
1. Getting stories from sources to desk — the ingest-to-draft flow
2. Drafting and refining articles — compose and chat workflow
3. Editorial review and handoff — the review workflow
4. Monitoring and alerts — standing watchlist behavior
5. Team workflow and roles — how editorial teams operate inside the product
6. Delivery and quotas — what happens when stories are published (including quota behavior — this must be addressed honestly)
7. WordPress and integrations — how published content moves downstream

---

### 3.4 — Social Proof and Trust Signals

Write placeholder structures for the types of proof that would work for this product and user, based on what you know about the workflows.

**Testimonial frames** (3 templates, each targeting a different user type from Phase 1)
Write the shape of what a real testimonial would say, identifying: the role, the before state, the specific product behavior they'd call out, and the outcome they'd claim. These are not fabricated quotes — they are briefs for real quote collection.

**Metric hooks** (3–5 metric shapes)
Identify what would be measurable and believable for this product's users. Not vanity metrics. Metrics that connect directly to the before/after states in Phase 1.

Example structure: `[User type] [does X] [Y% faster / in Y minutes instead of Y hours / without Z step]`

---

### 3.5 — Pricing Page Copy

**Pricing section headline** (under 10 words)
Not "Simple, transparent pricing." Connects to what users get, not how pricing works.

**Plan descriptions** — for each plan in the product:

```
Plan name: [from product]
Who it's for: [1 sentence, specific user situation — not "individuals and small teams"]
What it unlocks: [the specific capabilities or limits that define this tier's value — honest about what the plan allows and doesn't allow]
Headline for this plan: [under 8 words, from the user's perspective]
CTA: [2–4 words]
```

**Quota and limits framing**
The product has real limits (daily story quotas, monitoring rule caps, seat counts, plan-gated integrations). Write copy that frames these honestly without hiding them or over-softening them. Users who hit limits should feel informed, not surprised.

---

### 3.6 — Onboarding and Empty State Copy

For the first-run and setup experience, write:

**Onboarding entry prompt** (headline + 1-sentence body)
What the user sees before they start setup. Sets expectations and motivates completion.

**Setup step labels and helper text** (for each major onboarding step found in the product report)
Label (under 5 words) + helper text (1 sentence that explains why this step matters, not just what it is)

**Empty states** (for each major surface that can be empty before data exists)
```
Surface: [feed, editorial queue, monitoring history, etc.]
Heading: [under 8 words — acknowledges the empty state without being apologetic]
Body: [1–2 sentences — what the user does next and what they'll see when they do]
CTA: [2–4 words]
```

---

### 3.7 — Sales and Outreach Copy

**Cold outreach premise** (2–3 sentences)
Written for the primary buyer persona. Opens with their situation, not the product. References a specific, real pain point from Phase 1 Before states.

**Demo request confirmation** (3–5 sentences)
What the user reads after requesting a demo. Sets expectations for what the demo covers. Does not list every feature.

**Objection handling — 3 common objections**
Based on the fears identified in Phase 1, write a direct, honest response to each objection. Not "great question" framing. Not deflection. Actual answers.

---

### 3.8 — SEO and Meta Copy

**Page title** (under 60 characters)
**Meta description** (under 155 characters, complete sentence, describes what the page helps the visitor accomplish)
**OG/social share text** (under 280 characters, for primary share scenario)

## Phase 4: Voice and Tone Reference

Generate a short working reference for whoever writes or edits copy after this command runs.

### Voice Characteristics (derived from product and user context)

Identify 3–4 genuine voice traits that fit this product and audience. Not generic brand adjectives. Each must have:
- A positive definition ("we are X")
- A negative boundary ("not Y")
- A copy example showing the difference

### Terms and Framing

```
Use: [preferred term]
Avoid: [term to replace]
Because: [why the distinction matters for this audience]
```

Generate this for any technically-loaded terms found in the product report that map to user-language alternatives.

### Things This Product Does Not Claim

List 3–5 things the copy must never claim, based on gaps or limitations found in the product report. These protect the brand from overpromising and help writers know where the edges are.

## Output File Generation

Write output to: `project-info/site-copy.md`

Structure:
1. Voice reference (Phase 4) — at the top, so writers have context before reading copy
2. Value proposition architecture (Phase 2)
3. All copy surfaces (Phase 3), in section order
4. User situation map (Phase 1) — at the bottom as reference, not as deliverable

Each copy block must be labeled with its surface and usage context. No section should contain strategy notes instead of actual copy. If a section cannot be completed because the product report lacks sufficient signal, state specifically what additional input is needed — do not write placeholder copy.

## Verification Requirements

Before finalizing output, run each piece of copy through these checks:

**The Literal Test**: Can this sentence be traced back to a specific, verifiable product behavior? If not, cut or rewrite it.

**The Feature-Name Test**: Does this sentence use an internal feature name, data model term, or technical mechanism as user-facing language? If yes, translate it.

**The Passive Test**: Is the product the subject of the sentence doing things to the user, or is the user the subject experiencing an outcome? Rewrite toward the user as subject.

**The Competitor Test**: Could a direct competitor claim the exact same thing without lying? If yes, the copy is not differentiated enough. Find the specific product behavior that makes this claim unique and make it visible.

**The Before Test**: Does this copy make sense to someone who has never heard of this product? Does it acknowledge the situation they're in before they found it? If the copy only makes sense once you already understand the product, it won't work at the top of the funnel.

**The Skeptic Test**: Would a journalist or analyst who covers this beat find this copy credible, or would they find it inflated? The standard is credibility, not enthusiasm.
